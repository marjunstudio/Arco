# ドキュメントのズレを直す

ドキュメントと実装が食い違っていることに気付いたときの手順。
**気付いた時点で必ずこれを通す。「あとでまとめて直す」はしない**（次のセッションには忘れている）。

## 1. 事実を確定させる

ズレを1件ずつ、この形に落とす。**推測で書かない。両方の `file:line` を実際に読んで取る。**

```
ドキュメント: AGENTS.md「動かせない制約」の表 → IPHONEOS_DEPLOYMENT_TARGET は 18.0
実装:         iosApp/iosApp.xcodeproj/project.pbxproj:224,283 → 18.2
```

（これは 2026-09-03 に実際に起きた例。判定は「B. 実装が方針違反」で、直したのはコード側だった）

複数のズレを1件に混ぜない。判定が型ごとに変わるため。

## 2. どちらが正しいかを決めつけない

**「実装がこうなっているからドキュメントを合わせる」を既定値にしてはいけない。**
ドキュメント側が意図した制約で、実装が間違っている場合がある。3つの型に分けて判定する。

| 型 | 見分け方 | 対応 |
|---|--|--|
| A. ドキュメントが古い | 実装が意図的に進んだ結果で、記述が過去の状態を指している | ドキュメントを直す |
| B. 実装が方針違反 | ドキュメントが「動かせない制約」「実装の決めごと」「やらないこと」として書いている | 実装を直す |
| C. 方針そのものを変えたい | 制約を変える判断が必要（対応 OS を下げる、分岐を増やす、構成を変える等） | **ユーザーに聞く。どちらも勝手に直さない** |
| D. ドキュメントが実装より先行している | 文書の冒頭に「**ステータス: 決定済み・未着手**」がある | **ズレではない。何も直さない。** 実装が追いついたらステータス表のほうを消す |

型 D を型 A と取り違えないこと。`docs/architecture.md` `docs/modules.md` `docs/conventions.md` は
**実装より先に決定を書いた文書**で、書かれた構成が存在しないのは現時点では正常な状態。
「`:core:model` が無いからドキュメントが古い」と判定して消しにかからない。

AGENTS.md の **「動かせない制約」「やらないこと」「設計方針」** に触れるズレは、原則 B か C として扱う。
ウィザードや外部ツールが生成した値は、方針より古いことがある（ここが A に見えて B であることが多い）。

## 3. 確認をとる

`AskUserQuestion` で、判定した型と対応案を提示する。

- 選択肢は「ドキュメントを直す」／「実装を直す」／「今は直さず、未確定としてドキュメントに残す」を軸にする
- 1つの質問に複数のズレを詰め込まない
- 型 A で内容が明らかに機械的（パス、行番号、タスク名、ディレクトリ表）なら、確認せず直してよい。ただし**直したことは報告する**

## 4. 直す先を間違えない

| 内容 | 書く場所 |
|---|--|
| 依存バージョンの数字 | `gradle/libs.versions.toml` のみ。**ドキュメントに数字を書かない** |
| 使用技術・設計方針・実装の決めごと・やらないこと・地雷・完了条件 | `AGENTS.md` |
| 層の責務・UiState の形・状態の置き場所・エラーの扱い・DI の方針 | `docs/architecture.md` |
| モジュール一覧・依存グラフ・iOS への `export`・モジュール追加手順 | `docs/modules.md` |
| パッケージ・命名・Composable の書き方・`Flow` の扱い・ドメイン用語 | `docs/conventions.md` |
| iOS 26/18・API 31 の分岐実装 | `docs/platform-branching.md` |
| アプリの説明・前提環境・セットアップ手順・起動コマンド・目次 | `README.md` |

- **`CLAUDE.md` は `@AGENTS.md` を import しているだけ。方針・規範を書き足すのは `AGENTS.md` 側。**
  `CLAUDE.md` に書くのは Claude Code 固有の指示（skill やプランモードの使い方）に限る
- **`README.md` に実装詳細を書き戻さない。** 設計・命名・モジュールの話は `docs/` に置き、README からはリンクで飛ばす。
  README が持つのは「動かすまで」と目次まで
- 同じことを2箇所に書かない。ズレの原因は常に二重管理

## 5. ズレやすい箇所

実装が進むと以下が腐る。関連する作業をしたら、ついでに見る。

| ドキュメントの記述 | 確認先 |
|---|--|
| iOS deployment target | `grep -n IPHONEOS_DEPLOYMENT_TARGET iosApp/iosApp.xcodeproj/project.pbxproj`（Debug / Release の2箇所。片方だけ直すのが典型的な事故） |
| minSdk / targetSdk / compileSdk / jvmTarget | `gradle/libs.versions.toml`、各 `build.gradle.kts` |
| iOS ターゲット構成、framework の baseName | `shared/build.gradle.kts` |
| モジュール構成 | **決定は `docs/modules.md`、現状は `settings.gradle.kts` の `include`。この2つが食い違っているのは今は正常**（型 D）。分割を実施したら両方を突き合わせる |
| 3枚（architecture / modules / conventions）のステータス表 | 実装が追いついたら消す。**消し忘れると「まだ無い」と誤読される**。逆に、実装前に消すと存在しないものを探させる |
| ドメイン用語の揺れ | `docs/conventions.md` の用語表と `grep -rn 'Place\|Destination' shared/src`。`Spot` 以外の語が出てきたら直す |
| ディレクトリ表 | 実際の `shared/src/*`、`androidApp/src/*`、`iosApp/*` |
| `expect` / `actual` の命名規則 | `grep -rn 'expect fun' shared/src/commonMain` |
| bundle id / 署名の仕組み | `iosApp/Configuration/Config.xcconfig` |
| コマンド | **実際に実行して確認する**（`./gradlew :shared:tasks --all` でタスク名を引く） |

## 6. 直したあと

- ドキュメントを直したら、同じ内容が他のファイルにも残っていないか `grep` する
- 実装を直したら、ビルド／テストを通してから完了とする。通っていないなら通っていないと言う
- 「動かせない制約」を変えたなら、**なぜ変えたかを1行残す**。理由のない制約は次に必ず破られる
- 型 C で保留にしたなら、AGENTS.md に「未確定」として書く。頭の中に置かない
